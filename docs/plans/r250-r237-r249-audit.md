`player@gomail.com` is a fabricated address. The domain is real — in-game
evidence in [`docs/03` §16](../03-questions-for-the-developers.md) shows

**The correct rule, from our own in-game evidence:**

| Send | `to:` | Result | Source |
|---|---|---|---|
| r211 mail-authoring probe, 3 mails, **editor-compiled export**, run by Zeis 2026-09-21 | none authored → runtime fills from `Mail.getPlayerEmail()` | **all three arrived** (W-01 green, inbox observed by a human) | `QE24-Playtest-MailAuthoring.md` W-01; `QE24-TestResults-MailAuthoring.md:82` |

So a `to:` is **not** what loses a mail — a `to:` naming a mailbox that does not
exist is. r249's headline ("**the `to:` field is what loses a mail**", README
r249 row, `docs/03` §25, `QE24-TestResults-DynProbe-ModSettings.md:154`) is
over-generalised from one fabricated address and is directly contradicted by
W-01, where a `to:` filled from `getPlayerEmail()` delivered three mails.

**The shipped editor is not broken by this.** `runtimeSource.ts:1429-1430`
fills `to` with the author's value or `getPlayerEmail()`, and that exact code
path is what W-01 ran green. See §5 for the one caveat that remains.

## 2. r245's "calling context" verdict is refuted by the probe's own data

r245 concluded the page-mail failure was "pinned to the calling context, not
the permission", on this A/B (still in `docs/03` §25):

| Sent from | Arrived? |
|---|---|
| quest `OnStart()` — trusted context | yes |
| page button via `HackhubSDK.Mail.send` — page context | no |

That A/B moved **two** variables at once. Reading the probe source:

1. `OnStart` mail — trusted context, **no `to`** → arrived (`mod.js:58`).
2. page button — page context, **`to: player@gomail.com`** → lost (`mod.js:296`).
3. **`Events.emit` bridge → the top-level trusted listener**, **`to: player@gomail.com`** → also lost, returning id `ra1DgwPOsB` (`mod.js:181-190`, `docs/03` §25).

Send 3 removes calling context as the variable entirely: a send performed in
trusted context failed exactly like the page-context one. The only difference
between the arrival and the two failures is the `to:` field.

Two consequences:

- `docs/03` §25's parenthetical — *"(That also rules the recipient out: the
  `OnStart` mail carries no `to` field and still landed.)"* — argues the
  opposite of what it claims. The arriving mail is the only one **without** a
  `to`; that identifies the recipient as the variable rather than excluding it.
- The `Events.emit` bridge workaround §25 asks the developer to confirm was
  **already built and already tested** (r246) and failed for the same reason.
  It is not a workaround for anything.

`docs/03` §25 is therefore filed with the game's developer on a false premise
and needs correcting. §14 (the genuine `UI.*` / `Mod "null"` refusal) is a
separate, independently evidenced finding and is **not** affected.

## 4. Live defect found: 7 QA fixture mails can never arrive

`reference/sdk-0.24-qa/projects/sdk-0.24-ingame-qa.project.json` carries an
authored `to: "player@gomail.com"` on **7 mail nodes in 5 quests**:

- `QESdk024EditorQa` — "QE24 editor QA scaffold"
- `QESdk024TimerQa` — "Timer A arrived (S-01 green)"
- `QESdk024TimerCalQa` — S-06, S-05, S-13 rows
- `QESdk024WaitMonthQa` — "Wait 1 minute fired", "Wait 1 month row fired now"

Any future run of those rows sends mail that is silently dropped, so the rows
would read as failures for a reason that has nothing to do with timers. The
generated `reference/sdk-0.24-qa/editor-export/` inherits it
(`dist/mod.js`, `src/index.ts`).

Honest limit on this finding: I could **not** establish whether these mails
arrived in the September runs. The runtime logs delivery for every mail
(`runtimeSource.ts:1499-1506`: `delivered` or `was accepted … but is not in the
inbox`), and the pasted September logs
(`QE24-TestResults - Timer-Rows.md`) contain **zero** occurrences of either
line — `grep -c -i delivered` returns 0. So `STATUS.md:618`'s "Timer A's
mail/toast landed" is not backed by a delivery log line in the evidence on
file. It may have been observed on screen; the logs do not say. Whether the
`to:` predates or postdates those runs is unrecoverable from a squashed
history. The fix is the same either way: remove the field.

## 5. One open question in shipped code (decision needed, not shipped here)

`runtimeSource.ts:1429`:

```js
var to = mailTo[node.id] || __QE.safe(function () { return sdk.Mail.getPlayerEmail ? sdk.Mail.getPlayerEmail() : ""; });
if (to) direct.to = to;
```

Zeis's ground truth is that **leaving `to` empty defaults to the player's
address**. The runtime instead substitutes `getPlayerEmail()`. Two readings of
W-01 are consistent with the evidence:

- `getPlayerEmail()` returns the real address → the fill is harmless; or
- it returned `""`/threw, `__QE.safe` swallowed it, `if (to)` skipped the field
  → the mails arrived *because* `to` was omitted, and `getPlayerEmail()` has
  never actually been proven to round-trip.

Nothing in the repository distinguishes these — no QA row prints
`getPlayerEmail()`'s value beside an arrival. The probe's mail C
(`dynprobe/dist/mod.js:526-530`) is exactly that test and has not been run.

Options, smallest first:

1. **Leave the runtime alone**; run probe 1.3.0 once and let mail C settle it.
2. **Omit `to` when the author left it blank**, keeping an authored `to` as-is.
   Strictly smaller and uses the documented default instead of an unverified
   SDK call whose failure mode is silent. Evidence for it: Zeis's ground truth,
   the Nemesis reference mod (`docs/02-editor-shell.md:1440-1456` — the only
   mod whose mails demonstrably arrived, and it sends
   `Mail.send({ from, subject, content })` with no `to`), and r49
   (`docs/02-editor-shell.md:2212`) which already named our
   `getPlayerEmail()`-derived `to` as the prime suspect for the game-side
   `moment` RFC2822 warning. Changes compiler output → bumps `EDITOR_BUILD`
   (AR13) and re-pins `compile.test.ts:2248,2382`.

**Not shipped in this round.** Per the standing rule, a fix on a theory is what
cost this project r41/r43/r55/r60/r61/r66; option 2 is defensible but is a
behaviour change to a path that has in-game green evidence, so it is Zeis's
call.
