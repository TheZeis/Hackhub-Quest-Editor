Give the player an objective, and make it tick

You'll need
Objective · When event
Takes
About five minutes

The idea

An objective on its own is a line in the player's journal that never ticks. It has no idea what completing it means. The node that knows is When event — it listens to the game. It fires when the thing you asked about happens. Wire the two together and the objective finishes itself.

This is the single most common shape in a quest. It is also the one thing the editor refuses to let you forget. An objective with nothing wired into its Trigger socket is flagged as an error. The player can never finish the quest.

Steps

  1. Drag an Objective from Objectives onto the canvas.
  2. Select it and fill in Shown to the player — the line that appears in the journal. Write it as an instruction: Download the manifest from the warehouse server.
  3. Give it an Identifier — a short name only other nodes see, like get-manifest. You will not need it here, but later objectives can unlock behind this one.
  4. Drag a When event from Triggers onto the canvas, beside the objective.
  5. Select it and open Game event. Pick the event that means the player did the thing — for a downloaded file over ssh, Terminal.SSH.FileDownload.
  6. Add a condition under Only when so any file download does not count. Set the field to name, the rule to contains, and the value to manifest.
  7. Drag a wire from the When socket on the trigger into the Trigger socket on the objective. This wire is a different colour from a flow wire, because it is a different kind of connection.
  8. Check the status bar. The error should be gone.

Variations

  • Several things must happen first. Add a second When event and wire both into the same Trigger socket. The objective ticks when any one of them fires — so for "do all three", gate them behind each other instead.
  • Hide it until later. Turn on Hidden until unlocked on the objective and wire another objective's Unlocks socket into its Unlocked by socket. It stays out of the journal until then.
  • Run something when it ticks. Wire the objective's On complete socket to whatever should happen next — a payment, a phone call, the next objective.

If it doesn't work

  • The objective still shows an error. The wire went into In instead of Trigger. Delete it and try again — the two sockets are different colours for exactly this reason.
  • It ticks too early, or on the wrong file. The condition is too loose, or missing. Narrow it, or add a second clause.
  • It never ticks even though the player did the thing. The event you picked is not the one the game fires for that action. A file pulled over ssh raises two events. Listening to only one is a common miss — see the objective never ticks.
  • You still can't see why. Drop a Debug probe after the objective and run a dry run. It prints what each node does when it fires , and whether it fires at all. So you can tell if the trigger is even going off.

Send the player a message from an NPC

You'll need
a Dialogue node, and one node already in your story to hang it off
Takes
about five minutes for a single message

The idea

One Dialogue node carries a whole conversation: every line spoken, and every reply the player can pick. You write it in the inspector, and the game shows it in the player's own phone, chat or inbox.

Choose the form to match what the story needs. A call interrupts, so it reads as urgent. Mail leaves something the player can go back to. Kisscord reads like a chat and suits a back-and-forth. WeeChat is a public room, so other characters can be present.

Steps

  1. Put the node down. Dialogue is in the Comms group of the palette.
  2. Wire it into the story. Drag a Then wire from the node before it into In. Nothing reaches a node until something points at it, and the node will say Unreachable until you do.
  3. Choose the form. Open the node and set Conversation type to Phone call, Kisscord chat, E-Mail or WeeChat. Each one opens its own editor, so pick before you write much.
  4. Write the script. Every line has a speaker and the words they say. On a call the speaker box reads Caller. Add a line for everything spoken, including the player's side.
  5. Decide when the story moves on. On a call, Out fires chooses between "When the call ends" and "Right after starting the call". Leave it on the first unless something has to happen while the player is still listening.

Variations

  • Let the player answer, and get it wrong. Give a line a button for the player to pick. The Wrong socket then carries the story somewhere else. You can write what the character says when the answer misses.
  • Make a chat arrive later. Kisscord and WeeChat carry a Play when the story reaches this node toggle. Left off, the conversation is handed to the game when the quest starts — the safe, normal choice. Switched on, nothing appears until the story arrives, so a chat can land on a timed beat.
  • Know what switching that on costs. A live chat is delivered one message at a time. Player replies, uploads and "unlocks after" steps only work in the ordinary script. The game also does not clean live messages up when the quest ends.
  • Keep a paper trail. Use E-Mail when the player should be able to find the message again later.
  • Attach a file to a Kisscord chat. It does not reach the player as a file. It arrives as a line of text standing in for it, so write around that.

If it doesn't work

  • The node says Unreachable. Nothing is wired into In. Connect it to the chain that should run it — nodes do nothing until something points at them.
  • Everything after the call runs straight away. Out fires is set to "Right after starting the call". Switch it back to "When the call ends".
  • You changed the conversation type and the script looks empty. Each form keeps its own script, so nothing is lost. Switch back and yours is still there.
  • A timed chat never plays. The toggle is on but nothing is wired into the node, so the story never arrives. Wire it in, or turn the toggle off.
  • You still cannot see why. Put a Debug probe after the node and run a dry run. It prints what each node does when it fires. So you can tell whether the story reaches the conversation at all.

Make a message arrive only after something else happens

You'll need
a Dialogue node, a Branch, and a When event to gate it on
Takes
about ten minutes

The idea

A conversation is worth more once the player has earned it. The message that lands after the break-in lands harder than the one waiting at the start.

A conversation has no "wait until" field. You build the wait out of two pieces: something that notices the thing happened. The other is a Branch that only lets the story through when it did.

Steps

  1. Put the conversation down. A Dialogue node, written the way you want it. Wire nothing into it yet.
  2. Notice the thing. Drop a When event node and pick the Game event the game fires for the action you care about.
  3. Add the gate. Drop a Branch. Drag a wire from the event node's When socket into the branch's Trigger socket. That wire is cyan, because it carries a condition rather than the story.
  4. Say what has to be true. On the branch, Test against reads details from the event that fired. It can also read quest data you stored earlier with a Set quest data node. Add your clauses under Take the "Yes" path when. Every clause has to hold for the Yes path to run.
  5. Let the story in. Drag a Then wire from the branch's Yes into the conversation's In.
  6. Give No somewhere to go. Both paths need an end. Leave No hanging and the node says Dead end, because the quest stalls if the player takes it.

Variations

  • Gate on an objective instead. An Objective has an On complete socket. Wire that straight into the conversation and the message lands the moment the objective ticks — no branch needed.
  • More than two outcomes. Chain branches. Wire the first one's No into a second branch's In, and each one splits again. The canvas stays readable.
  • Test something that happened earlier. Store it with a Set quest data node, then point Test against at that value instead of at the event.
  • Gate the message, not the story. Leave the conversation on the main path and put the gate in front of something else. The player gets the briefing either way, and only the reward waits.

If it doesn't work

  • The wire into Trigger will not connect. You are dragging from a flow socket. Wires only join sockets of the same kind, and a condition wire has to come from a When socket.
  • The message never arrives. The event you picked is not the one the game fires for that action. See the objective never ticks, which covers the same mistake.
  • Both paths run. Your clauses are empty or too loose, so the Yes path always holds. Narrow them — every clause has to be true.
  • The node says Dead end. One of Yes or No has no wire. Both need somewhere to go, even if No leads straight to the end.
  • You still cannot see why. Put a Debug probe on each side of the branch and run a dry run. It prints what fires, so you can see which way the gate sent the story.

Pay the player, and charge them

You'll need
a Pay the player node and a Charge the player node, each somewhere on your story path
Takes
about five minutes

The idea

Money is how a quest tells the player what the work was worth. A payment at the end says it counted. A charge at the start says the tools cost something.

Two nodes, one for each direction. Pay the player deposits. Charge the player takes. Both sit on the story path, run when the story reaches them, and hand it straight on.

Steps

  1. Put the node on the path. Both are in the Effect group. Wire a Then wire in and another out.
  2. Set the amount. On Pay the player, Amount is the dollars to deposit. A new node starts at 100.
  3. Name it on the statement. Description is the label the player sees in their bank. Write it the way the client would.
  4. Say who sent it. From IBAN and From name fill in the transfer details. Each has a generator beside it, so you do not have to invent an account number.
  5. Charging works the same way, with one extra choice. On Charge the player, pick Amount type first. Fixed amount takes the number you type. Percentage of balance takes a slice of whatever the player has when the node runs.

Variations

  • Charge a slice instead of a sum. Percentage of balance scales to how rich the player is. It works out to whole dollars. A small balance can round down to a much smaller charge than you pictured.
  • Put a tag in the description. The statement label is filled in when the node runs. A tag you stored earlier can appear in it — the client's own name, for instance.
  • Charge for the tools, not the job. Put the charge before the work rather than after it. The player pays, then finds out what they bought.
  • Pay in stages. Two payments read better than one big transfer. Half on the briefing, half when the objective ticks.

If it doesn't work

  • Nothing happens and nothing complains. The amount is 0 or blank. A payment of nothing is skipped outright, and the story carries on as if the node had run. There is no warning for this, so check the field.
  • The player was charged less than you set. You used Percentage of balance and it rounded down to whole dollars.
  • The transfer shows no sender. Fill From IBAN and From name together, or leave both empty. They travel as a pair.
  • You cannot find a percentage option on Pay the player. There is not one. Taking a slice is the Charge node's job. Older projects that had one still run as written.
  • You still cannot see why. Put a Debug probe either side of the node and run a dry run. It prints what fires, so you can tell whether the story reaches the payment at all.

Branch the story on something the player did

You'll need
a Branch node, something to test, and somewhere for both routes to end up
Takes
about ten minutes

The idea

Two routes through one quest. The player who got in quietly and the player who set off the alarm both finish. Neither sees the other's version.

The two routes do not need two copies of the ending. Only one side of a branch ever runs. Both can walk back into the same node and it runs once.

Steps

  1. Choose the moment. Pick the point where the routes part. Everything before it stays shared, and everything after can be shared again.
  2. Drop the Branch. It is in the Flow group. Wire the story into In.
  3. Give it something to test. A branch reads details from the event that fired, or quest data you stored earlier. Drag a When wire from a When event node into Trigger, or point Test against at stored data instead.
  4. Write the condition. Under Take the "Yes" path when, add your clauses. Every one has to hold, or the No path runs.
  5. Build both routes. Wire Yes and No into whatever each version needs. Keep them short — the differences are the point.
  6. Bring them back together. Wire the end of both routes into one shared node. It runs once, because only one route ever got there.

Variations

  • Three outcomes or more. Chain branches. Wire the first one's No into a second branch's In, and each one splits again. The canvas stays readable.
  • Test something from earlier in the quest. Store it with a Set quest data node when it happens, then point Test against at that value. The branch no longer needs an event.
  • Tidy wires that cross. Double-click a wire to drop a Reroute into it. Wires route through it, and it changes nothing about the story.
  • Branch on a wrong answer instead. A Dialogue node's Wrong socket is already a fork. Use it when the split is about what the player said.

If it doesn't work

  • The node says Dead end. One of Yes or No has no wire, and the quest stalls if the player takes it. Both need somewhere to go.
  • Both routes run. Your clauses are empty or too loose, so the Yes path always holds. Narrow them — every clause has to be true.
  • The shared ending plays twice. That node has another wire into it as well. A node runs every time the story reaches it, so give the shared node one way in.
  • The wire into Trigger will not connect. Wires only join sockets of the same kind. A condition wire has to come from a When socket, not a flow one.
  • You still cannot see which way it went. Put a Debug probe on each route and run a dry run. Only the one the story took will print.

Ask the player for a passphrase, with a wrong-answer route

You'll need
Ask player, a clue that reveals the passphrase, and three possible follow-ups
Takes
About five minutes

The idea

Ask player opens a question box when the story reaches it. It accepts one line of text.

Turn on Mask typing to hide the answer while the player enters it.

With Accept set to check an answer, the node shows Correct and Wrong outputs. Closing the box uses Cancelled.

The player should have a way to discover the passphrase before this question appears.

Steps

  1. Choose the moment. Put the question after the player can find the passphrase.
  2. Add Ask player. Find it under Effects. Connect the previous story step to its In socket.
  3. Write the question. Fill Question with words that tell the player what to enter. Add a Title only if the question needs a heading.
  4. Hide the typing. Turn on Mask typing.
  5. Set the accepted answer. Set Accept to Exactly this answer. Fill Answer to accept with the passphrase from the clue.
  6. Set capitalisation. Leave Case sensitive off unless capital letters matter to the puzzle.
  7. Connect all three routes. Send Correct to the success route. Send Wrong to a hint or other consequence. Connect Cancelled to what should happen if the player closes the box.

Variations

  • Let capitalisation vary. Leave Case sensitive off. That is the default.
  • Accept extra words. Choose Contains these words if the player may include other text.
  • Use the answer later. Fill Save answer as only if later messages or branches need the typed text.

If it doesn't work

  • No Wrong output appears. Change Accept from Any submitted text to Exactly this answer.
  • Every answer takes Wrong. Check Answer to accept. An empty accepted answer cannot match, and the editor warns you.
  • The right word still fails. Turn off Case sensitive unless capitals are part of the puzzle.
  • Closing runs the wrong reply. Wire Cancelled separately. Closing does not use Wrong.
  • The dry run chooses the wrong route. A dry run uses the node's default or a simulated answer. Test in-game with a correct answer, a wrong answer and a closed box.

Build a website the player has to find

You'll need
Websites, one public clue, and a way to tell the player the host
Takes
About ten minutes

The idea

A website can carry a clue in plain sight. The player visits it in the game's browser and reads the page.

The site host is the address the player types. Give the player that host before you ask them to visit.

A mail, dialogue or earlier clue can provide it. This walkthrough keeps the home page public and searchable.

Steps

  1. Start blank. If the builder is empty, click Blank website. Otherwise click Add website, then choose Blank website. It starts with a Home page at / and sample text.
  2. Choose a host. Replace example.net in Host with a distinctive address. Give each site in this mod its own host.
  3. Edit the public page. Select Home at /. Leave the editor on visual, replace the sample words, and put your clue in visible text. Change Browser tab title if you want a different tab label.
  4. Keep it findable. Leave Listed in the in-game search on. It starts on by default. Turning it off hides the page from search, but its direct address still works.
  5. Check the result. Select preview. Check the host and path at the top. Replace any sample text you missed.
  6. Send the clue. Put the same host in a message the player sees before they need the site. The home page needs no extra path. If you add another page, share its path or link to it from the home page.

Variations

  • Add another page. Use New page and choose a public layout, such as Newsletter article. Link it from the home page or tell the player its path.
  • Gate progress on a visit. Give the target page its own path. Follow the objective walkthrough with Browser.WebsiteOpened and match Url to that path. This detects opening the page, not reading it.
  • Make the host a lookup target. Add Register domain only if the player should look up the host with whois. The builder's Host stays the browser address.

If it doesn't work

  • The export flags the host. Replace example.net with a distinctive host. Two sites in this mod cannot share one host.
  • The page is missing from search. Turn on Listed in the in-game search. If it is off, the player needs its direct address.
  • The browser cannot find the page. Check Host and Path. An in-site link must match a page path on this site.

Hide a page from in-game search

You'll need
Websites, a page to unlist, and optionally When event
Takes
About five minutes

The idea

Turning off Listed in the in-game search removes a page from search. It does not make the page private.

Players can still type its full address. They can also find its path with dirhunter. Use this for discoverable pages, not secrets.

Steps

  1. In Websites, select the site and page. Note the site's Host and the page's Path.
  2. Turn off Listed in the in-game search. The page leaves search but stays reachable by its address.
  3. Give the player the site's host. Include a clue about the site if they must search for its hidden path.
  4. To check a completed search, add a When event. Choose Terminal.Dirhunter.
  5. Under Only when, add a condition. Type results as the event detail, choose contains, and enter the page path as the value.
  6. Connect the trigger's When wire to an objective's Trigger socket. This checks discovery, not whether the page was opened.
  7. To check a visit, choose Browser.WebsiteOpened instead. Match Url to the page path and connect its When wire.

Variations

  • Give the player a direct link. Put the complete address in a message. The search listing does not block that route.
  • Keep the rest of the site public. Change the listing setting on the individual page you want to unlist.

If it doesn't work

  • The page still appears in search. Check the listing setting on that page, not another page on the site.
  • The objective ticks on another result. Match results against the complete path you expect.
  • The hidden page opens from a typed address. That is expected. The setting removes search listings; it does not block direct access.

Put a file on a remote device

You'll need
Create network and Place files
Takes
About five minutes

The idea

Remote files are included with a matching network device at export. They are there before the player connects.

The editor places them under the account marked Accepts reverse TCP. If none is marked, it uses the first account.

Steps

  1. Add a Create network node and choose the device that should hold the clue. The game assigns its address.
  2. Add Place files. Set Where to A remote device.
  3. Set Device IP to the same address as the target. For the main network device, use {{data.targetIp}}.
  4. Set Parent folder, such as ~/docs. Choose a folder the player can find in their account.
  5. Click Add file. Fill in Name, Extension and Contents.
  6. Give the player a way into that device and account. See Create network for account and port settings.

Variations

  • Put a folder tree there. Set Parent folder to a path such as ~/docs, or add a folder row.
  • Write to the player's PC instead. Set Where to The player's PC. That copy is written when the story reaches the node.

If it doesn't work

  • The export says the device was not found. Match Device IP to the address of a device in this quest's network.
  • The file is missing after login. Check which account accepts reverse TCP. Otherwise, the first account owns the files.
  • The folder is empty. Add at least one file and fill in its contents.

Gate progress on a target scan

You'll need
Create network, Objective and When event
Takes
About five minutes

The idea

An objective can wait for the player to scan one particular address. Its completion can release the next story beat.

The game assigns the network address. Use {{data.targetIp}} instead of copying an address from an example.

Steps

  1. Add an Objective that asks the player to scan the target.
  2. Add a When event node. Choose Terminal.NmapScan under Game event.
  3. Under Only when, add a condition. Type ip as the event detail, choose is exactly, and enter {{data.targetIp}} as the value.
  4. Connect When from the trigger to the objective's Trigger socket. Do not connect it to the flow input.
  5. Connect the objective's On complete output to the next story node. That beat starts after the matching scan.

Variations

  • Ask for an ordinary scan. Match ip only. A version scan is not required.
  • Show a reply after completion. Connect the objective's completion output to a message or another objective.

If it doesn't work

  • The objective never ticks. Check that the scan targeted this quest's device and the condition uses ip.
  • The address changes between builds. Use {{data.targetIp}} for the game-assigned target instead of a typed example address.
  • The next beat starts too soon. Connect it to On complete, not directly after the trigger.

Give the player a lead to look up

You'll need
Tool response and a domain the player can investigate
Takes
About five minutes

The idea

A clue can name a domain, then let the player ask whois for its record. The reply is text you provide.

Register domain is separate. Add it only when the player should also resolve that domain to an address.

Steps

  1. Add a Tool response node to the quest.
  2. Set Tool to whois. Set Keyed by to the exact domain the player will type.
  3. Write one fact per line under Response. Use labels such as Domain, IP, Registrant and Email.
  4. Give the same domain to the player in a message, website or other clue. Keep its spelling identical to Keyed by.
  5. To count the lookup, add a When event. Choose Terminal.Whois and match its domain to the clue.
  6. Connect the trigger's When wire to the objective's Trigger socket.

Variations

  • Let the player use nslookup too. Add Register domain and point Resolves to at the intended address.
  • Use a changing network address. Put {{data.targetIp}} in the response's IP line.

If it doesn't work

  • The normal Whois result appears. Check the tool name and exact input in Keyed by.
  • The response is blank. Add labeled lines under Response.
  • nslookup cannot resolve the name. A Whois response does not register a domain. Add Register domain separately.

Match a tool addon to its target

You'll need
A tool mod's .json pack, a target in your quest, and the matching game mod
Takes
About ten minutes

The idea

A loaded pack lets the editor compare your declared targets with a tool mod's stated requirements. It cannot test the mod in the game.

Target warnings appear only when the pack is loaded, the quest uses it, and the quest declares a target.

Steps

  1. Ask the tool mod's author for its .json pack. Open Addons and choose Load a pack (.json).
  2. Keep in mind that the pack is stored in this browser, not in your project. Players still need the matching game mod.
  3. Read the pack's target requirements. Give your target a listed service and fill in any required port versions or domain weaknesses.
  4. For example, the Recon-NG pack accepts services such as http. It also recognizes aliases such as https and web.
  5. For that pack, add version text to each service port. Add a supported weakness, such as RCE, to a registered domain.
  6. Use an event, data node or addon node from the pack in the quest. The editor checks targets only when the quest shows it uses that pack.
  7. Open Export mod or Dry run. Read the target warnings and adjust any unmatched services, versions or weaknesses.

Variations

  • Check another pack. Use the rules in that pack instead of copying the Recon-NG example.
  • Keep a local checklist. Addons stay in this browser's storage, so load the pack again in another browser.

If it doesn't work

  • No target warnings appear. Confirm the pack is loaded, the quest uses it, and a target is declared.
  • A service warning appears. Change the target's service to one accepted by the pack.
  • A version warning disappears. That confirms a version value is present. It does not prove that version fits the tool's real requirements.

Route on whether a supported app is installed

You'll need
App Install Check and a desktop app your story may require
Takes
About five minutes

The idea

App Install Check checks desktop apps, not terminal commands. It routes the story through Installed or Missing.

It does not install the app. Give players who lack it another way forward.

Steps

  1. Place the check. Put App Install Check before a story beat that assumes the player can open an app. Connect the previous step to its In socket.
  2. Choose the app. Select its desktop name under App name. Supported choices include Kisscord, Wireshark and Database Manager.
  3. Connect both routes. Send Installed to the app task. Send Missing to a fallback or another route.
  4. Save the full app list only when needed. Leave Also save the list of installed apps on if a later node needs it. Set Save the list as to choose its name.
  5. Keep terminal commands out of this check. Commands such as lynx cannot be checked as desktop apps.

Variations

  • Use another supported app. Select the name shown in the desktop app list.
  • Check the full list later. Keep the list-saving option on and use its saved name in a later node.

If it doesn't work

  • The Missing route always runs. Select a supported app name. A terminal command cannot match here.
  • The story stops on one outcome. Connect both Installed and Missing outputs.
  • A later node cannot read the app list. Turn on Also save the list of installed apps and reuse the same name.

Chain conversations together

You'll need
Dialogue and the next story beat
Takes
About five minutes

The idea

A Dialogue node has an Out route and a Wrong route. Phone calls can wait to finish before the next beat.

A typed reply reaches Wrong only when its answer setting selects that route.

Steps

  1. Add a Dialogue node and choose Phone call. Connect the previous story node to its In socket.
  2. Write the call, then set Out fires to When the call ends.
  3. Add the next conversation. Connect the first node's Out to the next node's In.
  4. For each typed reply, set On a wrong answer to Node's Wrong output. Change this in the script editor.
  5. Connect Wrong to a hint or retry route. Give the wrong answer somewhere useful to go.

Variations

  • Start the next beat immediately. Set Out fires to Right after starting the call. The call can still be in progress.
  • Give a wrong reply a separate ending. Connect Wrong to a different message or branch.

If it doesn't work

  • The next call starts too soon. Set Out fires to When the call ends.
  • A wrong reply does not branch. Set On a wrong answer to Node's Wrong output.
  • The wrong route stops. Connect the node's Wrong output to a follow-up.

End the story cleanly with Complete quest

You'll need
Complete quest, a final story beat and optional rewards
Takes
About five minutes

The idea

Complete quest is a terminal ending with no output. Put closing story and payments before it, or under On quest complete.

Quest Money and XP are completion rewards. Pay the player is a separate transfer node.

Steps

  1. In Quest settings, set the quest's Money and XP rewards.
  2. Leave Complete automatically off when this node should control the ending.
  3. Place the closing message, payment or notification before Complete quest.
  4. Connect the final story beat to the node's In socket. Nothing connects after its ending.
  5. Put optional follow-up work under the quest's On quest complete entry.

Variations

  • Let completion pay a reward. Set Money or XP in Quest settings.
  • Run cleanup afterward. Use On quest complete for work that should start after the quest ends.

If it doesn't work

  • The quest ends before the closing message. Turn off Complete automatically and use the ending node.
  • A payment never happens. Connect it before Complete quest or under On quest complete.
  • You cannot wire a next beat from the ending. That node has no output. Move the beat before it or into the completion entry.

Customize a template safely

You'll need
Templates and a saved project file if you want to keep your current work
Takes
About five minutes to load; longer to customize

The idea

The picker has 14 entries: 12 templates and two Reference sheets. First Contact is a Beginner template with eight nodes.

Choosing an entry replaces the current project and clears undo history. Autosave is not a versioned backup.

Steps

  1. Save what you have. Use top-bar Save or Export current quest in the picker.
  2. Open Templates in the top bar, or click Browse 14 templates on the welcome panel.
  3. Choose First Contact to study an eight-node Beginner quest. Read its connections before changing them.
  4. Edit the quest's messages, objectives and connections to fit your story. Keep the saved project file as your recovery copy.
  5. To reopen saved work, use top-bar Load or Import a quest file in the picker.

Variations

  • Browse reference sheets. Node Reference and Quest Cookbook show examples; they are not starter quests.
  • Share your starting project. Use Export current quest to make a project file another editor can import.

If it doesn't work

  • Your old work is gone. Loading a template replaces the project. Restore it with the saved project file.
  • You expected autosave to restore an earlier version. Autosave keeps the current draft, not a version history. Save a separate project file first.
  • The reference sheet is not a playable quest. Choose a quest template such as First Contact instead.

Update an exported quest

You'll need
The saved project file and the exported mod folder
Takes
About ten minutes

The idea

The saved project is the editable source. The exported .zip is finished game output, not a project you can reopen.

Keep the same Mod id for an update. Increase Version before you export again.

Steps

  1. Open the saved project with top-bar Load. Do not try to load the exported .zip.
  2. Make and save your changes in the editor. Keep the original project file for future edits.
  3. Open the inspector's Mod tab. Leave Mod id unchanged and increase Version.
  4. Open Export mod, read its report, then choose Download .zip.
  5. Unzip the new archive. Replace the old extracted mod folder inside the game's mods/ folder.

Variations

  • Recover the editable project. Use the saved project file, or ask its author for one. The exported archive cannot restore the canvas.
  • Ship through the Workshop. Increase Version before each upload, as the editor's hint says.

If it doesn't work

  • The game still loads the old files. Replace the extracted folder under mods/, not the zip beside it.
  • The update appears as a different mod. Check that Mod id still matches the original.
  • You only have the exported archive. It is not editable. Find the saved project file or rebuild the quest in the editor.
