How do I…

Walkthroughs, each one solving a single thing an author actually wants. The ones not written yet are listed below. You can see what is coming and ask for the one you need.

These are not a feature of the editor. They are arrangements other authors have built, written out as steps you can follow. Each one names the nodes it uses, how long it takes. It also says why the arrangement works, and the two or three ways it usually goes wrong. They are drawn from the built-in templates and from how the game's own quests are put together.

Give the player an objective, and make it tick

You'll need
Objective · When event
Takes
About five minutes

The idea

An objective on its own is a line in the player's journal that never ticks. It has no idea what completing it means. The node that knows is When event — it listens to the game. It fires when the thing you asked about happens. Wire the two together and the objective finishes itself.

This is the single most common shape in a quest. It is also the one thing the editor refuses to let you forget. An objective with nothing wired into its Trigger socket is flagged as an error. The player can never finish the quest.

Steps

  1. Drag an Objective from Objectives onto the canvas.
  2. Select it and fill in Shown to the player — the line that appears in the journal. Write it as an instruction: Download the manifest from the warehouse server.
  3. Give it an Identifier — a short name only other nodes see, like get-manifest. You will not need it here, but later objectives can unlock behind this one.
  4. Drag a When event from Triggers onto the canvas, beside the objective.
  5. Select it and open Game event. Pick the event that means the player did the thing — for a downloaded file over ssh, Terminal.SSH.FileDownload.
  6. Add a condition under Only when so any file download does not count. Set the field to name, the rule to contains, and the value to manifest.
  7. Drag a wire from the When socket on the trigger into the Trigger socket on the objective. This wire is a different colour from a flow wire, because it is a different kind of connection.
  8. Check the status bar. The error should be gone.

Variations

  • Several things must happen first. Add a second When event and wire both into the same Trigger socket. The objective ticks when any one of them fires — so for "do all three", gate them behind each other instead.
  • Hide it until later. Turn on Hidden until unlocked on the objective and wire another objective's Unlocks socket into its Unlocked by socket. It stays out of the journal until then.
  • Run something when it ticks. Wire the objective's On complete socket to whatever should happen next — a payment, a phone call, the next objective.

If it doesn't work

  • The objective still shows an error. The wire went into In instead of Trigger. Delete it and try again — the two sockets are different colours for exactly this reason.
  • It ticks too early, or on the wrong file. The condition is too loose, or missing. Narrow it, or add a second clause.
  • It never ticks even though the player did the thing. The event you picked is not the one the game fires for that action. A file pulled over ssh raises two events. Listening to only one is a common miss — see the objective never ticks.
  • You still can't see why. Drop a Debug probe after the objective and run a dry run. It prints what each node does when it fires , and whether it fires at all. So you can tell if the trigger is even going off.

Send the player a message from an NPC

You'll need
a Dialogue node, and one node already in your story to hang it off
Takes
about five minutes for a single message

The idea

One Dialogue node carries a whole conversation: every line spoken, and every reply the player can pick. You write it in the inspector, and the game shows it in the player's own phone, chat or inbox.

Choose the form to match what the story needs. A call interrupts, so it reads as urgent. Mail leaves something the player can go back to. Kisscord reads like a chat and suits a back-and-forth. WeeChat is a public room, so other characters can be present.

Steps

  1. Put the node down. Dialogue is in the Comms group of the palette.
  2. Wire it into the story. Drag a Then wire from the node before it into In. Nothing reaches a node until something points at it, and the node will say Unreachable until you do.
  3. Choose the form. Open the node and set Conversation type to Phone call, Kisscord chat, E-Mail or WeeChat. Each one opens its own editor, so pick before you write much.
  4. Write the script. Every line has a speaker and the words they say. On a call the speaker box reads Caller. Add a line for everything spoken, including the player's side.
  5. Decide when the story moves on. On a call, Out fires chooses between "When the call ends" and "Right after starting the call". Leave it on the first unless something has to happen while the player is still listening.

Variations

  • Let the player answer, and get it wrong. Give a line a button for the player to pick. The Wrong socket then carries the story somewhere else. You can write what the character says when the answer misses.
  • Make a chat arrive later. Kisscord and WeeChat carry a Play when the story reaches this node toggle. Left off, the conversation is handed to the game when the quest starts — the safe, normal choice. Switched on, nothing appears until the story arrives, so a chat can land on a timed beat.
  • Know what switching that on costs. A live chat is delivered one message at a time. Player replies, uploads and "unlocks after" steps only work in the ordinary script. The game also does not clean live messages up when the quest ends.
  • Keep a paper trail. Use E-Mail when the player should be able to find the message again later.
  • Attach a file to a Kisscord chat. It does not reach the player as a file. It arrives as a line of text standing in for it, so write around that.

If it doesn't work

  • The node says Unreachable. Nothing is wired into In. Connect it to the chain that should run it — nodes do nothing until something points at them.
  • Everything after the call runs straight away. Out fires is set to "Right after starting the call". Switch it back to "When the call ends".
  • You changed the conversation type and the script looks empty. Each form keeps its own script, so nothing is lost. Switch back and yours is still there.
  • A timed chat never plays. The toggle is on but nothing is wired into the node, so the story never arrives. Wire it in, or turn the toggle off.
  • You still cannot see why. Put a Debug probe after the node and run a dry run. It prints what each node does when it fires. So you can tell whether the story reaches the conversation at all.

Make a message arrive only after something else happens

You'll need
a Dialogue node, a Branch, and a When event to gate it on
Takes
about ten minutes

The idea

A conversation is worth more once the player has earned it. The message that lands after the break-in lands harder than the one waiting at the start.

A conversation has no "wait until" field. You build the wait out of two pieces: something that notices the thing happened. The other is a Branch that only lets the story through when it did.

Steps

  1. Put the conversation down. A Dialogue node, written the way you want it. Wire nothing into it yet.
  2. Notice the thing. Drop a When event node and pick the Game event the game fires for the action you care about.
  3. Add the gate. Drop a Branch. Drag a wire from the event node's When socket into the branch's Trigger socket. That wire is cyan, because it carries a condition rather than the story.
  4. Say what has to be true. On the branch, Test against reads details from the event that fired. It can also read quest data you stored earlier with a Set quest data node. Add your clauses under Take the "Yes" path when. Every clause has to hold for the Yes path to run.
  5. Let the story in. Drag a Then wire from the branch's Yes into the conversation's In.
  6. Give No somewhere to go. Both paths need an end. Leave No hanging and the node says Dead end, because the quest stalls if the player takes it.

Variations

  • Gate on an objective instead. An Objective has an On complete socket. Wire that straight into the conversation and the message lands the moment the objective ticks — no branch needed.
  • More than two outcomes. Chain branches. Wire the first one's No into a second branch's In, and each one splits again. The canvas stays readable.
  • Test something that happened earlier. Store it with a Set quest data node, then point Test against at that value instead of at the event.
  • Gate the message, not the story. Leave the conversation on the main path and put the gate in front of something else. The player gets the briefing either way, and only the reward waits.

If it doesn't work

  • The wire into Trigger will not connect. You are dragging from a flow socket. Wires only join sockets of the same kind, and a condition wire has to come from a When socket.
  • The message never arrives. The event you picked is not the one the game fires for that action. See the objective never ticks, which covers the same mistake.
  • Both paths run. Your clauses are empty or too loose, so the Yes path always holds. Narrow them — every clause has to be true.
  • The node says Dead end. One of Yes or No has no wire. Both need somewhere to go, even if No leads straight to the end.
  • You still cannot see why. Put a Debug probe on each side of the branch and run a dry run. It prints what fires, so you can see which way the gate sent the story.

Pay the player, and charge them

You'll need
a Pay the player node and a Charge the player node, each somewhere on your story path
Takes
about five minutes

The idea

Money is how a quest tells the player what the work was worth. A payment at the end says it counted. A charge at the start says the tools cost something.

Two nodes, one for each direction. Pay the player deposits. Charge the player takes. Both sit on the story path, run when the story reaches them, and hand it straight on.

Steps

  1. Put the node on the path. Both are in the Effect group. Wire a Then wire in and another out.
  2. Set the amount. On Pay the player, Amount is the dollars to deposit. A new node starts at 100.
  3. Name it on the statement. Description is the label the player sees in their bank. Write it the way the client would.
  4. Say who sent it. From IBAN and From name fill in the transfer details. Each has a generator beside it, so you do not have to invent an account number.
  5. Charging works the same way, with one extra choice. On Charge the player, pick Amount type first. Fixed amount takes the number you type. Percentage of balance takes a slice of whatever the player has when the node runs.

Variations

  • Charge a slice instead of a sum. Percentage of balance scales to how rich the player is. It works out to whole dollars. A small balance can round down to a much smaller charge than you pictured.
  • Put a tag in the description. The statement label is filled in when the node runs. A tag you stored earlier can appear in it — the client's own name, for instance.
  • Charge for the tools, not the job. Put the charge before the work rather than after it. The player pays, then finds out what they bought.
  • Pay in stages. Two payments read better than one big transfer. Half on the briefing, half when the objective ticks.

If it doesn't work

  • Nothing happens and nothing complains. The amount is 0 or blank. A payment of nothing is skipped outright, and the story carries on as if the node had run. There is no warning for this, so check the field.
  • The player was charged less than you set. You used Percentage of balance and it rounded down to whole dollars.
  • The transfer shows no sender. Fill From IBAN and From name together, or leave both empty. They travel as a pair.
  • You cannot find a percentage option on Pay the player. There is not one. Taking a slice is the Charge node's job. Older projects that had one still run as written.
  • You still cannot see why. Put a Debug probe either side of the node and run a dry run. It prints what fires, so you can tell whether the story reaches the payment at all.

Branch the story on something the player did

You'll need
a Branch node, something to test, and somewhere for both routes to end up
Takes
about ten minutes

The idea

Two routes through one quest. The player who got in quietly and the player who set off the alarm both finish. Neither sees the other's version.

The two routes do not need two copies of the ending. Only one side of a branch ever runs. Both can walk back into the same node and it runs once.

Steps

  1. Choose the moment. Pick the point where the routes part. Everything before it stays shared, and everything after can be shared again.
  2. Drop the Branch. It is in the Flow group. Wire the story into In.
  3. Give it something to test. A branch reads details from the event that fired, or quest data you stored earlier. Drag a When wire from a When event node into Trigger, or point Test against at stored data instead.
  4. Write the condition. Under Take the "Yes" path when, add your clauses. Every one has to hold, or the No path runs.
  5. Build both routes. Wire Yes and No into whatever each version needs. Keep them short — the differences are the point.
  6. Bring them back together. Wire the end of both routes into one shared node. It runs once, because only one route ever got there.

Variations

  • Three outcomes or more. Chain branches. Wire the first one's No into a second branch's In, and each one splits again. The canvas stays readable.
  • Test something from earlier in the quest. Store it with a Set quest data node when it happens, then point Test against at that value. The branch no longer needs an event.
  • Tidy wires that cross. Double-click a wire to drop a Reroute into it. Wires route through it, and it changes nothing about the story.
  • Branch on a wrong answer instead. A Dialogue node's Wrong socket is already a fork. Use it when the split is about what the player said.

If it doesn't work

  • The node says Dead end. One of Yes or No has no wire, and the quest stalls if the player takes it. Both need somewhere to go.
  • Both routes run. Your clauses are empty or too loose, so the Yes path always holds. Narrow them — every clause has to be true.
  • The shared ending plays twice. That node has another wire into it as well. A node runs every time the story reaches it, so give the shared node one way in.
  • The wire into Trigger will not connect. Wires only join sockets of the same kind. A condition wire has to come from a When socket, not a flow one.
  • You still cannot see which way it went. Put a Debug probe on each route and run a dry run. Only the one the story took will print.
